# `internal/db/AGENTS.md`

The rules for migrations and schema now that Quark's database has two engines: SQLite, the default and the
reference, and PostgreSQL, the second backend being added under #2955. The root
[`AGENTS.md`](../../AGENTS.md) covers when a change may touch the database at all and how migrations are
numbered; [`sql/queries/AGENTS.md`](../../sql/queries/AGENTS.md) covers the queries.

This file sits in `internal/db/` and not beside the migrations because `database.go` embeds the whole
`migrations/` directory into the binary. Nothing but migrations goes in there.

> **Status.** The server runs on either engine, chosen at startup. Music search and a few other features are
> SQLite-only for now:
> [`docs/architecture/data.md`](../../docs/architecture/data.md#what-does-not-work-on-postgresql-yet) lists
> them.

## One schema, written once per engine

Each engine has its own migration set, and the two describe the same logical schema: the same tables,
columns, nullability, defaults and uniqueness.

| Engine     | Migrations                         | Generated package    |
| ---------- | ---------------------------------- | -------------------- |
| SQLite     | `internal/db/migrations/`          | `internal/db`        |
| PostgreSQL | `internal/db/migrations_postgres/` | `internal/db/pgdb`   |

The PostgreSQL set is a sibling directory, not `migrations/postgres/`: the embed and
`scripts/check-migration-numbers.bash` both read `migrations/` whole.

- **A schema change is a migration in each set, with the same number, in the same pull request.** The
  PostgreSQL set starts at `032_baseline`, the whole schema as it stood after SQLite's migration 032, so that
  from 033 on a number means the same change on both engines.
- **`make check/migrations` fails a migration in one set and not the other.** Above the PostgreSQL baseline
  every file name is in both sets. A change one engine needs and the other does not still takes the number on
  both, as a migration that does nothing on the other engine, with a comment saying so: `041_content_search` is
  the example. `TestPostgresSchemaMatchesSQLite` catches the drift in what the sets build once the PostgreSQL
  job runs: it compares every table's columns, in order, by name, nullability and mapped type. It does not
  compare indexes, defaults or constraints.
- **Every migration has a `.down.sql`** that drops exactly what its `.up.sql` created.
  `TestPostgresMigrationsRunDownAndUpAgain` runs the PostgreSQL set down and up again.
- **Not in the PostgreSQL schema:** `file_content_fts` and its triggers, and `music_tracks_fts` and its
  triggers. Both are FTS5. Content search's counterpart is `file_content.search_vector`, a generated
  `tsvector` with a GIN index (`041_content_search`), the one column only one schema has; music search has
  none yet. The `file_content` and `music_tracks` tables themselves are in both schemas, because the
  generated queries write to them.

sqlc reads an engine's migrations as that engine's schema, so the column types chosen here decide the Go
types sqlc generates.

## Type mapping

Both generated packages must come out with **identical Go types** for every column, parameter and result.
That is what lets one interface describe both, and it turns a type that drifts between the engines into a
compile error rather than a runtime surprise.

| SQLite                                | PostgreSQL                                            | Go          |
| ------------------------------------- | ----------------------------------------------------- | ----------- |
| `INTEGER`, including a 0/1 flag       | `BIGINT`                                              | `int64`     |
| `INTEGER PRIMARY KEY AUTOINCREMENT`   | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `int64`     |
| `BOOLEAN`                             | `BOOLEAN`                                             | `bool`      |
| `DATETIME`                            | `TIMESTAMPTZ`                                         | `time.Time` |
| `REAL`                                | `DOUBLE PRECISION`                                    | `float64`   |
| `BLOB`                                | `BYTEA`                                               | `[]byte`    |
| `TEXT`                                | `TEXT`                                                | `string`    |

A nullable column is nullable on both sides, so both get the same `sql.Null*` type.

- **Never `INTEGER`, `INT` or `SERIAL` on PostgreSQL.** They are 32-bit and generate `int32`. `REAL` is 32-bit
  there too.
- **A 0/1 flag declared `INTEGER` on SQLite stays a number.** `users.is_admin` and `groups.builtin` are
  `BIGINT` on PostgreSQL and queries compare them with `0` / `1`. Only a column declared `BOOLEAN` on SQLite
  is `BOOLEAN` on PostgreSQL.
- **Case-insensitive uniqueness is an expression index.** SQLite's `UNIQUE (name COLLATE NOCASE)` is
  PostgreSQL's unique index on `LOWER(name)`; queries order with `LOWER(...)` on both.
- **A SQLite type outside this table needs a row here first.** `TestPostgresSchemaMatchesSQLite` fails on a
  SQLite column type it has no mapping for.

## Functions SQLite has and PostgreSQL lacks

A shared query may call a SQLite function only when the PostgreSQL schema defines a function of the same
name for the form the query uses (rule 16 in `sql/queries/AGENTS.md`). Such a function is part of the
PostgreSQL schema: it is created by a migration, it carries a comment naming the queries that rely on it and
the forms it does not support, and it rejects an unsupported form rather than returning something
plausible. `032_baseline.up.sql` defines two, `datetime(text, text)` and `json_extract(text, text)`;
`TestSQLiteNamedFunctions` covers each form in use.

An index on such an expression calls the same function in both schemas, as `idx_jobs_backup_target` does with
`json_extract`, or the planner cannot match the query to the index.

## Callers hold `db.Querier`

Code outside this package takes the generated `db.Querier` interface, never the concrete `*db.Queries`, so the
engine behind it can change without touching a caller.

- **`db.NewQueries(sqlDB)` builds one from a pool**, for the engine that pool is connected to. Do not call
  the generated `db.New` or `pgdb.New` outside this package and its tests: they bind one engine's queries
  to whatever they are given.
- **A transaction is `db.InTx`.** `WithTx` is not on the interface. The raw `*sql.Tx` code in `pkg/backup` and
  `internal/db/reset.go` is left as it is.
- **Nothing outside this package branches on the engine.** `db.BackendOf(sqlDB)` reads it from the driver
  the pool was opened with, and `NewQueries` and `InTx` are its callers. Code that finds itself wanting to
  branch on it needs a query both engines accept, or a per-engine query, instead.
- **The one thing a caller may do is refuse.** A feature built on raw SQL only SQLite accepts starts with
  `db.RequireSQLite(sqlDB, "<Feature>", <issue>)` and returns its `*db.UnsupportedError`, which `serverutil`
  answers as `501`. Today that is music search. A feature that needs one raw statement per engine keeps both
  here instead, as `db.SearchContent` does for content search. The chat and vault backups refuse PostgreSQL by design
  rather than for now: they return `backup.ErrDatabaseBackedUpSeparately`, because the operator's PostgreSQL
  backups carry those rows, and a snapshot backup leaves both files out.
- **An error inside `db.InTx` ends the transaction.** On PostgreSQL a failed statement aborts it and every
  later statement is refused, where SQLite carries on. Return the error, a unique violation included
  (`sqlutil.IsUniqueConstraintErr` recognizes both engines'), and never continue past one.
- **The PostgreSQL `db.Querier` is the generated `postgresQueries`**, in this package. `pgdb.Queries` cannot
  satisfy the interface itself, because sqlc gives each package its own parameter and result structs; the
  adapter converts between them. It lives here and not in `pgdb` so that `NewQueries` can return it: `pgdb`
  imports nothing of Quark's, and the other way round would be an import cycle.

## Opening a database

`db.ConfigFromEnv` is the one place that reads the choice: `QUARK_DB_BACKEND` is `sqlite` (also when unset
or empty) or `postgres`, anything else is an error naming the two, and `postgres` needs `QUARK_DATABASE_URL`.
The URL carries a password, so no log line or error repeats it.

`db.ConnectToDatabase` is what the server calls. It opens SQLite's `quark.db` as it always has, or, when the
environment names PostgreSQL, hands over to `db.ConnectToPostgres(url)` (`connect_postgres.go`):

- **The pool** is bounded like SQLite's, and unlike it gives idle connections back and retires old ones. The
  constants carry the reasoning.
- **The session is pinned to UTC, and a `TIMESTAMPTZ` scans into a UTC `time.Time`**, which is what the SQLite
  DSN's `_timezone=UTC` gives.
- **Migrations run through golang-migrate's pgx v5 driver** from the embedded `migrations_postgres/`. It
  takes a session-level advisory lock (`pg_advisory_lock`) around creating `schema_migrations` and around the
  run, so two servers starting at once on one database are safe: the second waits, then finds nothing to do.
- **The server is checked before anything is migrated.** PostgreSQL older than 14, `fsync = off` or
  `synchronous_commit = off` stops startup and changes nothing (`checkPostgresDurability`, and
  [`docs/architecture/durability.md`](../../docs/architecture/durability.md#postgresql) for why).
- **There is no reset on PostgreSQL, and there must never be one.** A database that does not answer, a dirty
  flag, a version this build does not have, or tables Quark did not make each stop startup with an error
  saying what was found and what to do, and change nothing. SQLite's startup (`initSchema`) refuses the same
  way, and sets a database from the pre-#1758 numbering aside; none of that code is reached from this path,
  and PostgreSQL has no such legacy to set aside.

`db.ResetDatabase` is a different thing: the factory reset an admin asks for by name. It works on both
engines. On PostgreSQL (`reset_postgres.go`) it runs the migrations' own down files and then the up files in
one transaction, carries the same kept tables across, and moves their identity sequences past the rows it
restored.

`db.MoveToPostgres` (`move_postgres.go`, the `quark move-to-postgres` command) copies an install's SQLite
file, opened read-only, into an empty PostgreSQL database in one transaction and checks every table's count.
It reads the tables, columns and foreign keys from the PostgreSQL catalog, so a new table or column needs
nothing there. A column type outside the mapping above needs a case in `convertForPostgres`, and a table the
server rebuilds from disk goes in `rebuiltTables`. [`docs/architecture/postgres-move.md`](../../docs/architecture/postgres-move.md)
has the rest.

## What PostgreSQL does differently at run time

The schema and the queries are held equal by the tests. These are not, and code has to allow for them:

- **A `TIMESTAMPTZ` keeps microseconds**, where SQLite's `DATETIME` text keeps whole seconds. Never rely on two
  rows made in the same second tying, or on a time read back being equal to the second.
- **A sequence does not give an id back.** A refused insert still uses one up.
- **There is no single writer.** A guard that counts and then changes is exact on SQLite and can race on
  PostgreSQL at `READ COMMITTED` unless it takes a row lock first. The last-admin and last-channel-owner guards
  do: `LockActiveAdmins` and `LockChatChannel`, a no-op `UPDATE` as the transaction's first statement (#3171).
  A new count-then-change guard does the same, or puts a constraint behind it. The one still open is the
  `ClaimJob` lane limit, listed in
  [`docs/architecture/data.md`](../../docs/architecture/data.md#what-behaves-differently) and tracked in #2964.

## Generated code

Never edit any of these by hand. Change the query or the migration and run `make generate/backend/sqlc`,
which runs sqlc for both engines and then the adapter generator.

- **sqlc's output:** `*.sql.go`, `models.go`, `db.go` and `querier.go`, in `internal/db/` and in
  `internal/db/pgdb/`. sqlc does not remove a generated file whose source `.sql` was renamed or deleted;
  delete the stale `*.sql.go` in both packages yourself.
- **`internal/db/querier_postgres.go`**, written by `internal/db/genpgadapter` from the `Querier` interface
  in `internal/db`. When it stops compiling, the two engines disagree about a query's signature or a column's
  type: fix the query or the schema, never the adapter.

## Checking the PostgreSQL side

```bash
make serve/postgres      # the development PostgreSQL, from compose.yaml
make test/db/postgres    # prepare every generated statement, compare the schemas, run the queries, connect and migrate
```

`dbtest.PostgresURL(t)` gives a test the URL of an empty schema of its own. The tests that use it, in
`internal/db` and `internal/db/pgdb`, skip by name on the default backend. With the backend set to PostgreSQL and no
database reachable they fail and say to run `make serve/postgres`. Each test's schema is dropped when
it ends, so they leave the development database as they found it. CI runs them in `test.yml`'s
`test-postgres` job.
